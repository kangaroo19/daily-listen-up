product-manager와 frontend-developer 서브에이전트를 사용해서 `docs/exec-plans/active` 안에 2번 세부 작업지시서를 작성해줘.

현재 `docs/exec-plans/index.md` 기준 2번 작업은 `Firebase Functions 백엔드 기반 세팅`이다.
프론트 전용 작업지시서가 아니라, React 프론트엔드와 Firebase Functions 백엔드가 함께 있는 프로젝트 기준으로 작성한다.

먼저 다음 문서를 읽고 기준을 맞춰줘.

- `INTRODUCE.md`
- `docs/exec-plans/index.md`
- `docs/design-docs/style-guidelines.md`

역할 분담:

- product-manager:
  - 각 작업의 사용자 가치, 기능 범위, 제외 범위, 완료 기준을 정의한다.
  - MVP 범위가 커지지 않도록 조정한다.
  - `INTRODUCE.md`의 정책과 어긋나는 요구를 막는다.
  - Toss 로그인, 프로모션, Ads처럼 Apps in Toss 정책이나 사용자 흐름 정책이 필요한 경우 `$docs-search`로 공식 문서를 확인한다.

- frontend-developer:
  - 각 작업을 실제 React 프론트엔드 구현 관점으로 구체화한다.
  - 화면, 상태, 데이터 흐름, Firebase Functions API 호출 경계, 로딩/에러/빈 상태를 검토한다.
  - TDS와 Apps in Toss WebView 환경에서 구현 가능한 형태로 정리한다.
  - SDK 호출 방식, WebView 제약, TDS 컴포넌트 기준이 필요한 경우 `$docs-search`로 공식 문서를 확인한다.

- backend 관점:
  - Firebase Functions 디렉터리 구조, 함수 엔트리, API 경계, 요청/응답 계약을 검토한다.
  - Firebase Admin SDK, Firestore 접근, secret/env 관리, 배포와 검증 기준을 정리한다.
  - Toss 서버 API 연동이 필요한 작업에서는 클라이언트가 아니라 Firebase Functions에서 처리해야 하는 범위를 구분한다.
  - Firebase Functions, Firebase Auth, Firestore 기준이 필요한 경우 공식 Firebase 문서를 확인한다.
  - 별도 backend 서브에이전트를 사용할 수 없다면 메인 스레드가 이 관점을 보완한다.

메인 스레드 역할:

- 두 서브에이전트의 결과를 비교하고 충돌을 정리한다.
- 최종 문서 형식과 용어를 통일한다.
- 실제 파일 작성은 메인 스레드가 담당한다.
- `completed` 폴더에는 아직 문서를 만들지 않는다.

작성 대상 파일은 `docs/exec-plans/index.md`의 전체 작업 목록에 있는 파일명 그대로 사용한다.

각 active 작업지시서 문서 형식은 아래 템플릿을 따른다.

# N. 작업명

## 목적

이 작업을 통해 사용자가 어떤 경험을 할 수 있어야 하는지 짧게 설명한다.

## 구현 범위

이번 작업에서 구현할 내용을 bullet로 정리한다.

## 제외 범위

이번 작업에서 하지 않을 내용을 bullet로 정리한다.

## 구현 기준

프론트엔드와 Firebase Functions 구현 시 지켜야 할 화면, 상태, 데이터 흐름, API 연동, secret/env, 배포 기준을 정리한다.

## 상태 및 예외 처리

로딩, 빈 상태, 실패, 재시도, 중복 요청, API 오류, 외부 서비스 실패 등 이 작업에서 고려해야 할 상태를 정리한다.

## 완료 기준

작업이 끝났다고 판단할 수 있는 빌드, 타입체크, 에뮬레이터, 배포 준비, 화면 동작 확인 기준을 bullet로 정리한다.

## Git 전략

이 작업을 진행할 때 사용할 브랜치, 커밋, PR 기준을 정리한다.

- 최신 `dev` 기준에서 `codex/{번호}-{작업명}` 형식의 작업 브랜치를 만든다.
- 의미 있는 기능 단위마다 커밋한다.
- 작업 완료 후 같은 번호의 completed 문서를 작성한다.
- 작업 브랜치에서 `dev`로 PR을 보낸다.
- 예외가 필요한 작업은 이 섹션에 예외 사유와 진행 방식을 명시한다.

## 다음 작업과의 연결

이 작업이 다음 번호 작업에 어떤 입력이나 전제 조건을 넘기는지 정리한다.

문서 작성 규칙:

- 한국어로 작성한다.
- 환경세팅 설명은 최소화하고 실제 구현 지시 중심으로 쓴다.
- 별도 Express/Nest 서버 인스턴스는 만들지 않고 Firebase Functions를 백엔드로 본다.
- Firebase Functions 백엔드 작업은 구현 범위, API 계약, secret/env, Firestore Admin SDK 사용, 배포/검증 기준을 포함한다.
- 프론트 작업은 Firebase Functions 내부 구현에 결합하지 않고 요청/응답 계약과 어댑터 경계만 의존한다.
- `INTRODUCE.md`의 MVP 범위를 넘는 기능은 추가하지 않는다.
- `docs/design-docs/style-guidelines.md`의 톤처럼 간결하고 실행 가능한 문장으로 쓴다.
- 코드 구현은 하지 않는다.
- `docs/exec-plans/active` 안에 문서만 생성한다.
