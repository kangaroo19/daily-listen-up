# 10. TDS UI 정리, 테스트, 빌드 검증, MVP 완료 체크

## 목적

홈, 문제 풀이, 결과 화면과 서버 API 흐름을 MVP 기준으로 최종 점검한다.
TDS UI 일관성, 전체 테스트 시나리오, 빌드/실행 검증, 당일 완료와 중복 보상 방지까지 확인해 MVP가 제품 기준을 만족하는지 판단한다.

## 범위

- MVP 화면 범위인 홈, 문제 풀이, 결과 화면의 UI를 TDS 기준으로 정리한다.
- 제품 스펙의 핵심 문구, 상태, 버튼, 토스트가 구현과 일치하는지 확인한다.
- 로그인, 오늘 문제 조회, 오디오 1회 재생, 복수응답 선택, 전면형 광고 이후 답안 제출, 결과 확인, 포인트 지급 상태, 오답 재도전, 스크립트 보기, 완료 사용자 홈 재진입까지 전체 시나리오를 검증한다.
- Firebase Emulator 기준의 서버 API 검증과 프론트 로컬 실행 검증을 수행한다.
- 타입 검사, 테스트, 빌드, 로컬 실행 명령을 최종 확인한다.
- MVP 완료 기준과 남은 확인 필요 항목을 completed 문서에 정리할 수 있게 한다.

## 제외 범위

- 새로운 제품 기능, 새 화면, 새 API를 추가하지 않는다.
- MVP 기준을 넘는 디자인 개편이나 리브랜딩을 하지 않는다.
- ESLint, Prettier, TypeScript 설정값처럼 팀 결정이 필요한 항목을 임의로 변경하지 않는다.
- 운영 배포, 실제 포인트 정산, 운영 모니터링, 백오피스 구축은 이 작업에서 다루지 않는다.
- 제품 스펙과 충돌하는 내용을 임의로 고치지 않고 “확인 필요”로 남긴다.

## 확인 필요

- Toss 실제 SDK, Toss Ads, 비게임 프로모션 API가 로컬/검수 환경에서 제공하는 테스트 모드와 운영 전환 조건은 최종 구현 시 공식 문서와 운영 설정 확인이 필요하다.
- 최종 심사 제출용 스크린샷, 개인정보/약관 표기, Toss 검수 제출 양식은 현재 제품 스펙에 없으므로 필요 시 별도 작업으로 분리한다.

## 작업 체크리스트

- [ ] 작업 시작 시 `docs/exec-plans/completed/09-daily-completion-duplicate-guard-result.md`가 존재하면 먼저 읽고 상태 전이 표, 테스트 데이터, 남은 확인 필요 항목을 반영한다.
- [ ] 홈 화면이 `docs/product-specs/home.md`의 목적, 문구, CTA, 토스트 기준을 따른다.
- [ ] 문제 풀이 화면이 `docs/product-specs/quiz.md`의 오디오 1회 재생, 5개 선택지, 복수응답, 제출 조건을 따른다.
- [ ] 결과 화면이 `docs/product-specs/result.md`의 정답, 오답, 완료, 포인트 상태, 재도전, 스크립트 보기 기준을 따른다.
- [ ] 서버 API가 `docs/product-specs/backend.md`의 앱 세션, `quizDate`, `progressStatus`, `rewardStatus`, 중복 지급 방지 기준을 따른다.
- [ ] TDS 컴포넌트를 우선 사용했는지 화면별로 점검한다.
- [ ] 한 화면에 하나의 주요 목적만 보이도록 UI 밀도와 배치를 정리한다.
- [ ] 주요 액션이 모바일 WebView 하단에서 명확하게 보이고 다른 콘텐츠와 겹치지 않게 정리한다.
- [ ] 정답, 오답, 완료, 재도전, 보상 상태가 서로 혼동되지 않게 문구와 시각 표현을 정리한다.
- [ ] 홈에서 로그인 성공 후 오늘 문제 있음/없음 분기를 검증한다.
- [ ] 문제 풀이에서 오디오 자동 재생 방지와 1회 재생 제한을 검증한다.
- [ ] 복수응답 선택과 선택 0개 제출 비활성화를 검증한다.
- [ ] 답안 제출 후 전면형 광고 `dismissed` 이벤트 이후에만 정답 검증 API가 호출되는지 검증한다.
- [ ] 정답 제출 후 포인트 지급 상태가 결과 화면과 홈 재진입에서 일관되게 보이는지 검증한다.
- [ ] 오답 제출 후 보상형 광고 완료로 재도전하고, 재제출 시 재도전권이 소진되는지 검증한다.
- [ ] 정답과 오답 상태 모두에서 보상형 광고 완료 후 스크립트가 표시되는지 검증한다.
- [ ] 완료 사용자가 홈 재진입 시 결과 화면이나 문제 풀이 화면으로 이동하지 않는지 검증한다.
- [ ] 지급 실패 상태가 서버 기준으로 저장되고 홈 토스트와 결과 안내에서 확인되는지 검증한다.
- [ ] 같은 사용자와 같은 날짜에 중복 포인트 지급 요청이 발생하지 않는지 검증한다.
- [ ] API 실패, 광고 실패/취소, 문제 로딩 실패 상태에서 사용자가 다시 시도할 수 있는지 검증한다.
- [ ] 타입 검사, 테스트, 프론트 빌드, Functions 빌드 또는 Emulator 검증 명령을 실행한다.
- [ ] MVP 완료 여부와 남은 확인 필요 항목을 completed 문서에 기록할 수 있게 정리한다.

## 검증 체크리스트

- [ ] 홈, 문제 풀이, 결과 화면이 모바일 WebView 기준으로 주요 액션과 콘텐츠가 겹치지 않는다.
- [ ] 모든 화면에서 TDS 우선 원칙을 따르고 임의 디자인 시스템이 섞이지 않았다.
- [ ] 제품 스펙의 핵심 문구와 토스트가 구현에 반영되어 있다.
- [ ] 오늘 문제 없음 사용자는 홈에 머무르고 준비 중 토스트를 본다.
- [ ] 신규 사용자는 로그인 후 오늘 문제를 조회하고 문제 풀이 화면에 진입한다.
- [ ] 사용자는 오디오를 1회 듣고 5개 선택지 중 여러 개를 선택할 수 있다.
- [ ] 답안 제출은 전면형 광고 `dismissed` 이벤트 이후 서버 API로 처리된다.
- [ ] 정답 사용자는 `progressStatus = completed`가 되고 포인트 지급 상태를 확인한다.
- [ ] 오답 사용자는 `progressStatus = wrong`이 되고 보상형 광고 완료 후 재도전할 수 있다.
- [ ] 재도전 사용자는 `progressStatus = retry_unlocked`에서만 재제출할 수 있고 제출 시 재도전권이 소진된다.
- [ ] 정답과 오답 상태 모두에서 스크립트는 보상형 광고 완료 후에만 표시된다.
- [ ] 완료 사용자는 홈 재진입 시 홈 토스트만 보고 결과 화면으로 이동하지 않는다.
- [ ] 당일 완료, 중복 보상 방지, 지급 실패 상태가 서버 기준 테스트 또는 Emulator 검증으로 확인된다.
- [ ] 타입 검사 명령이 통과한다.
- [ ] 프론트 빌드 명령이 통과한다.
- [ ] Functions 빌드 또는 Emulator 검증 명령이 통과한다.
- [ ] 전체 테스트 또는 수동 시나리오 검증 결과가 completed 문서에 근거와 함께 기록된다.
