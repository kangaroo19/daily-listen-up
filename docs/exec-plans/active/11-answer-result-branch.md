# 11. 정답 확인 및 결과 분기 구현

## 목적

전면형 광고 완료 후에만 정답 여부를 확인하고, 정답이면 포인트 지급 흐름으로, 오답이면 보상형 광고 재도전 흐름으로 연결한다.

이 작업은 결과 확인과 분기 기준을 구현하는 작업이며, 포인트 지급 요청과 보상형 광고 재도전은 후속 작업에서 구현한다.

## 구현 범위

- 10번 작업에서 광고 완료와 서버 완료 반영이 끝난 상태인지 확인한다.
- `submissionId`를 사용해 서버 결과 확인 API를 호출한다.
- 서버 응답 기준으로 정답과 오답을 분기한다.
- 정답 상태와 오답 상태를 사용자가 즉시 구분할 수 있게 표시한다.
- 정답인 경우 11번 포인트 지급 요청 흐름으로 이동할 수 있는 연결점을 제공한다.
- 오답인 경우 12번 보상형 광고 재도전 흐름으로 이동할 수 있는 연결점을 제공한다.
- 결과 조회 로딩, 실패, 광고 미완료 차단 상태를 처리한다.
- 결과 확인 이후 사용자 진행 상태를 재조회하거나 서버 응답 기준으로 반영하는 기준을 정의한다.

## 제외 범위

- 답안 제출 API 구현
- 전면형 광고 SDK 호출 구현
- 포인트 지급 요청 API 호출과 지급 결과 처리
- 보상형 광고 호출과 재도전 권한 지급
- 재도전 횟수 정책 변경
- 오늘 학습 완료 화면 최종 구현
- 학습 통계, 공유, 랭킹, 복습 기능
- 클라이언트에서 `correctChoiceIndex`로 정답을 직접 판정하는 로직
- completed 문서 작성

## 구현 기준

- 광고 완료 전에는 결과 확인 API를 호출하지 않는다.
- 결과 화면은 `submissionId`와 광고 완료 상태가 모두 있을 때만 진입 가능하다.
- 광고 완료 상태가 없거나 서버가 결과 확인 불가를 반환하면 결과를 보여주지 않고 광고 단계로 되돌린다.
- 서버 API 인터페이스는 `GET /api/quiz-submissions/{submissionId}/result`를 기준으로 한다.
- 성공 응답은 다음 값을 기준으로 한다.
  - `quizDate`
  - `selectedChoiceIndex`
  - `isCorrect`
  - `correctChoiceIndex`
  - `script`
  - `promotionAmount`
  - `progressStatus`
  - `nextStep`
- `progressStatus`는 최소 `correct` 또는 `incorrect`를 기준으로 한다.
- `nextStep`은 정답 시 `point_reward`, 오답 시 `rewarded_retry`를 기준으로 한다.
- 정답 여부는 서버 응답의 `isCorrect`를 기준으로 판단한다.
- Firebase 문제 데이터의 `correctChoiceIndex`를 사용해 클라이언트에서 직접 판정하지 않는다.
- `correctChoiceIndex`와 `script`는 결과 확인 API 성공 이후에만 화면에 사용할 수 있다.
- 정답 상태는 포인트 지급 완료 상태가 아니다.
- 정답 화면에서는 11번 포인트 지급 요청이 아직 남아 있음을 상태와 CTA로 구분한다.
- 오답 상태는 재도전 가능 상태가 아니다.
- 오답 화면에서는 12번 보상형 광고를 완료해야 재도전할 수 있음을 짧게 안내한다.
- 보상 금액은 `정답 시 받을 수 있는 포인트`와 `지급 완료`를 혼동하지 않게 표현한다.
- 결과 화면은 TDS 기준의 상태 표시, 버튼, 레이아웃을 우선 사용한다.
- 화면 상단에는 결과 상태를 명확히 표시하고, 중앙에는 필요한 최소 설명을 두며, 하단에는 다음 행동 CTA를 둔다.
- 결과 조회 중에는 CTA를 비활성화한다.
- 결과 조회 실패 시 자동 반복 호출을 하지 않고 사용자의 재시도 액션을 기다린다.

## 상태 및 예외 처리

- `checking_eligibility`: 결과 확인 가능 조건을 확인 중이다.
- `loading_result`: 서버 결과 확인 API를 호출 중이다.
- `correct`: 정답이며 포인트 지급 요청 흐름으로 이어질 수 있다.
- `incorrect`: 오답이며 보상형 광고 재도전 흐름으로 이어질 수 있다.
- `blocked_by_ad`: 전면형 광고 완료 조건이 충족되지 않았다.
- `already_completed`: 서버가 오늘 학습 완료 상태를 반환했다.
- `error`: 결과 조회 실패, 응답 형식 오류, 네트워크 오류가 발생했다.
- 광고 완료 상태가 없으면 결과 API를 호출하지 않는다.
- 결과 조회 중 페이지를 떠나면 늦게 도착한 응답이 이전 화면 상태를 덮어쓰지 않게 한다.
- 서버가 `401`을 반환하면 로그인 상태 재확인이 필요한 상태로 처리한다.
- 서버가 `403` 또는 광고 미완료 상태를 반환하면 `blocked_by_ad`로 처리한다.
- 서버가 `409` 또는 이미 완료 상태를 반환하면 진행 상태를 재조회하고 완료 흐름으로 이동한다.
- 결과 응답에 필수 필드가 없으면 결과를 표시하지 않고 오류 상태로 처리한다.
- 정답 결과에서 포인트 지급 요청이 실패한 것처럼 보이는 문구를 미리 표시하지 않는다.
- 오답 결과에서 바로 다시 풀 수 있는 것처럼 보이는 CTA를 제공하지 않는다.

## 완료 기준

- 전면형 광고 완료 전에는 결과 화면에 진입하거나 결과 API를 호출하지 않는다.
- 서버 결과 확인 API 응답을 기준으로 정답과 오답이 분기된다.
- 정답 상태와 포인트 지급 완료 상태가 명확히 구분된다.
- 오답 상태와 재도전 가능 상태가 명확히 구분된다.
- 정답인 경우 11번 포인트 지급 요청 흐름으로 이어지는 연결점이 있다.
- 오답인 경우 12번 보상형 광고 재도전 흐름으로 이어지는 연결점이 있다.
- 결과 조회 실패와 광고 미완료 상태가 빈 화면이나 무한 로딩 없이 처리된다.
- `correctChoiceIndex`와 `script`는 결과 확인 이후에만 노출된다.
- 클라이언트가 Firebase 문제 데이터만으로 정답 여부를 판정하지 않는다.
- 포인트 지급 요청, 보상형 광고 호출, 완료 화면 최종 구현이 포함되지 않는다.

## Git 전략

- 최신 `dev` 기준에서 `codex/11-answer-result-branch` 형식의 작업 브랜치를 만든다.
- 의미 있는 기능 단위마다 커밋한다.
- 작업 완료 후 같은 번호의 completed 문서를 작성한다.
- 작업 브랜치에서 `dev`로 PR을 보낸다.
- 예외가 필요한 작업은 이 섹션에 예외 사유와 진행 방식을 명시한다.
- 서버 결과 확인 API가 준비되지 않았다면 mock 또는 임시 어댑터로 분기 상태만 검증하고 completed 문서에 남긴다.
