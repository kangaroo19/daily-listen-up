# 5. 사용자 식별 및 진행 상태 기준 정의

## 목적

토스 로그인 후 확보한 `userKey`를 기준으로 사용자의 오늘 학습 가능 여부와 완료 여부를 판단할 수 있게 한다.

이 작업은 화면을 만드는 작업이 아니라, 하루 1문제 정책과 00:00 KST 날짜 기준을 이후 문제 조회, 진입 화면, 결과 화면이 같은 방식으로 사용할 수 있게 고정하는 작업이다.

## 구현 범위

- `userKey`를 사용자 식별의 단일 기준으로 사용한다.
- KST 기준 오늘 날짜를 `YYYY-MM-DD` 형식의 `quizDate`로 정의한다.
- `userKey + quizDate` 기준으로 사용자 진행 상태를 조회하는 기준을 만든다.
- 사용자 진행 상태의 최소 필드와 상태값을 정의한다.
- 진행 상태가 없을 때의 `not_started` 판정 기준을 정의한다.
- 오늘 학습 완료 사용자가 문제 풀이 화면으로 다시 진입하지 못하는 분기 기준을 정의한다.
- 오답 후 재도전 가능 여부를 `hasEarnedRetry`와 상태값으로 판단하는 기준을 정의한다.
- 정답 검증, 광고 완료, 포인트 지급처럼 후속 작업에서 갱신할 상태 전이 지점을 문서화한다.

## 제외 범위

- 토스 로그인 호출과 로그인 결과 처리 변경
- Firebase 문제 데이터 조회
- 오늘의 문제 진입 화면 구현
- 오디오 재생 UI, 객관식 퀴즈 UI, 결과 화면 구현
- 답안 제출 API 호출과 정답 검증 구현
- 전면형 광고, 보상형 광고 SDK 호출 구현
- 토스 포인트 지급 요청과 지급 결과 조회 구현
- 서버의 중복 지급 방지, 정답 검증, 포인트 지급 로직 구현
- 학습 기록, 통계, 연속 학습, 랭킹, 프로필 화면
- 비로그인 사용자의 게스트 진행 상태

## 구현 기준

- 4번 작업에서 확보한 `authenticated` 상태와 `userKey`를 전제로 한다.
- 클라이언트는 Toss access token 또는 refresh token을 사용자 식별 기준으로 사용하지 않는다.
- `quizDate`는 KST 기준 `YYYY-MM-DD` 문자열로 통일한다.
- `quizDate` 계산은 공통 유틸리티 또는 공통 서비스 한 곳에서만 수행한다.
- 앱이 열린 상태에서 KST 자정이 지나면 기존 진행 상태를 그대로 재사용하지 않고 `quizDate`를 다시 계산한 뒤 조회한다.
- Firebase 진행 상태 문서는 `userKey + quizDate`로 유일하게 식별할 수 있어야 한다.
- Firestore 경로는 단일 문서 조회가 쉬운 `userProgress/{userKey}_{quizDate}` 형식을 우선 검토한다.
- 진행 상태 문서 필드는 다음 값을 기준으로 한다.
  - `userKey`
  - `quizDate`
  - `status`
  - `attemptCount`
  - `hasEarnedRetry`
  - `isPromotionGranted`
  - `promotionGrantKey`
  - `promotionStatus`
  - `lastSubmittedAt`
- `status`는 최소 `not_started`, `in_progress`, `submitted`, `correct`, `incorrect`, `completed`를 기준으로 한다.
- `promotionStatus`는 최소 `none`, `pending`, `granted`, `failed`를 기준으로 한다.
- 진행 상태 문서가 없으면 곧바로 쓰기 생성하지 않고 `not_started`로 해석한다.
- 진행 상태 생성 시점은 오늘 문제 시작 또는 답안 제출처럼 명확한 사용자 행동이 발생하는 시점으로 제한한다.
- 클라이언트는 진행 상태를 읽고 화면 분기에 사용하되, 정답 검증과 포인트 지급 확정은 서버 응답을 기준으로 한다.
- `isPromotionGranted`와 `promotionStatus`는 서버 지급 결과를 반영하는 값으로 보고 클라이언트에서 임의로 성공 처리하지 않는다.
- 오답 상태에서 `hasEarnedRetry`가 `false`이면 문제 풀이 재진입을 허용하지 않는다.
- 오답 상태에서 `hasEarnedRetry`가 `true`이면 같은 문제 재도전 가능 상태로 해석한다.
- 이미 `completed` 또는 포인트 지급 완료 상태인 사용자는 같은 `quizDate`에서 문제 풀이 화면으로 재진입하지 않는다.

## 상태 및 예외 처리

- `idle`: 로그인 전이거나 `userKey`가 아직 없다.
- `loading`: 오늘 진행 상태를 조회 중이다.
- `not_started`: 오늘 진행 상태 문서가 없고 아직 문제를 시작하지 않았다.
- `in_progress`: 오늘 문제 풀이에 진입할 수 있다.
- `submitted`: 답안을 제출했고 결과 확인 또는 광고 흐름이 진행 중이다.
- `incorrect`: 오답이며 재도전 가능 여부를 `hasEarnedRetry`로 판단해야 한다.
- `correct`: 정답 처리 이후 포인트 지급 또는 완료 전환이 남아 있다.
- `completed`: 오늘 학습이 완료되어 문제 풀이 재진입을 차단한다.
- `error`: 진행 상태 조회 실패, 권한 오류, 네트워크 오류, 응답 형식 오류가 발생했다.
- 진행 상태 조회 실패 시 문제 풀이 화면으로 낙관적으로 이동하지 않는다.
- 진행 상태 문서의 `quizDate`가 현재 KST `quizDate`와 다르면 현재 날짜 기준으로 다시 조회한다.
- 필수 필드가 누락되거나 알 수 없는 `status`가 오면 오류 상태로 처리한다.
- 동일한 상태 조회가 중복 실행되어도 화면이 서로 다른 상태로 흔들리지 않게 한다.
- 사용자가 새로고침하거나 앱에 재진입해도 같은 `userKey + quizDate` 기준으로 동일한 분기 결과를 얻어야 한다.

## 완료 기준

- `userKey + quizDate` 기준으로 오늘 진행 상태를 유일하게 조회하고 판정할 수 있다.
- KST `YYYY-MM-DD` 기준 날짜 계산 위치가 한 곳으로 정리되어 있다.
- 진행 상태 문서가 없는 경우와 조회 실패를 구분할 수 있다.
- 오늘 학습 완료 사용자가 문제 풀이 화면으로 재진입하지 않는 기준이 정의되어 있다.
- 오답 후 재도전 가능 여부가 `hasEarnedRetry`와 상태값으로 판단된다.
- 정답 검증, 광고 완료, 포인트 지급이 후속 작업에서 어떤 상태를 갱신해야 하는지 연결 지점이 명확하다.
- 클라이언트가 포인트 지급 성공이나 중복 지급 방지를 임의로 확정하지 않는다.
- 서버 구현 없이도 프론트에서 필요한 Firebase 진행 상태 인터페이스가 정리되어 있다.
- 6번과 7번 작업이 같은 `quizDate`와 진행 상태 기준을 재사용할 수 있다.
