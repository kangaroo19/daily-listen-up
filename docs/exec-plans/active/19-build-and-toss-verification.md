# 19. 빌드 및 Apps in Toss 실행 검증

## 목적

MVP 프론트엔드가 빌드 품질 기준을 통과하고, Apps in Toss WebView 환경에서 핵심 플로우에 진입할 수 있는지 확인한다.

이 작업은 검증 기준과 결과 기록을 만드는 작업이며, 발견된 모든 문제를 이 작업 안에서 고치는 것을 목표로 하지 않는다.

## 구현 범위

- 프로젝트의 빌드, 린트, 타입 체크, 포맷 체크 명령 실행 기준을 정리한다.
- 테스트 명령이 준비되어 있다면 17번 시나리오와 연결해 실행 기준을 정리한다.
- 필수 환경변수와 공개 가능한 클라이언트 설정 누락 여부를 확인한다.
- Firebase 초기화, Toss SDK 접근, Toss Ads 접근, 서버 API endpoint 설정을 확인한다.
- 로컬 브라우저 검증과 Apps in Toss WebView 검증을 구분한다.
- 샌드박스 앱에서 가능한 항목과 실제 토스앱/QR 검증이 필요한 항목을 구분한다.
- 로그인, 오늘 문제 진입, 오디오 재생, 선택지, 제출, 결과, 완료 화면 진입 가능 여부를 확인한다.
- 전면형 광고와 보상형 광고의 mock 검증, 실제 런타임 검증 여부를 분리해 기록한다.
- 검증 중 발견된 이슈를 blocker와 non-blocker로 분류한다.

## 제외 범위

- 서버 배포 또는 서버 구현
- 운영 배포 자동화 전체 구축
- 발견된 모든 버그의 대규모 수정
- 앱 심사 대응 문서 작성
- 운영 모니터링, 분석 이벤트, 대시보드 구축
- 비MVP 기능 검증
- completed 문서 작성

## 구현 기준

- 검증 명령은 프로젝트에 존재하는 스크립트를 기준으로 실행한다.
- 기본 검증 명령은 `npm run build`, `npm run lint`, `npm run typecheck`, `npm run format:check`를 기준으로 한다.
- 테스트 스크립트가 있으면 `npm test` 또는 프로젝트에서 정의한 테스트 명령을 함께 확인한다.
- `npm run format`처럼 파일을 수정하는 명령은 검증 명령으로 보지 않고, 실행 시 변경 여부를 반드시 확인한다.
- 필수 환경변수는 누락 시 앱이 조용히 실패하지 않는지 확인한다.
- 클라이언트 환경변수에는 공개 가능한 값만 있는지 확인한다.
- 로컬 브라우저에서 Toss SDK나 광고 API가 미지원인 상태는 실제 WebView 실패와 구분한다.
- Apps in Toss 샌드박스 앱에서는 가능한 기능과 미지원 기능을 나눠 기록한다.
- 공식 문서 기준으로 샌드박스에서 인앱 광고가 미지원이면 광고는 실제 토스앱 QR 또는 별도 실기기 검증 필요 항목으로 남긴다.
- 광고 검증은 `isSupported()`, `loadFullScreenAd`, `showFullScreenAd`, `dismissed`, `userEarnedReward` 이벤트 기준으로 확인한다.
- 포인트 지급은 로컬 mock 상태 전환과 서버 연동 검증을 분리한다.
- 오디오 재생은 로컬 브라우저와 WebView에서 모두 명시적 사용자 액션 이후 재생되는지 확인한다.
- safe area와 하단 CTA는 실제 모바일 WebView에서 겹침이 없는지 확인한다.
- 검증 실패 항목은 원인, 재현 조건, 출시 차단 여부를 함께 기록한다.

## 상태 및 예외 처리

- `build_passed`: 빌드가 성공했다.
- `build_failed`: 빌드가 실패했다.
- `script_missing`: 필요한 검증 스크립트가 없다.
- `env_missing`: 필수 환경변수가 누락되었다.
- `local_unsupported`: 로컬 브라우저에서 Toss 런타임 기능이 지원되지 않는다.
- `sandbox_supported`: 샌드박스에서 검증 가능한 항목이다.
- `sandbox_unsupported`: 샌드박스에서 검증할 수 없어 실기기 검증이 필요하다.
- `device_verified`: Apps in Toss 또는 실제 토스앱 환경에서 확인되었다.
- `blocked`: MVP 완료를 막는 차단 이슈다.
- `non_blocking_issue`: 후속 개선으로 넘길 수 있는 이슈다.
- 스크립트가 없으면 임의로 새 설정을 만들지 않고 누락 상태로 기록한다.
- 네트워크나 서버 미준비로 실패한 경우 프론트 문제인지 외부 의존성 문제인지 구분한다.
- 광고와 프로모션은 mock 통과만으로 실기기 검증 완료로 표시하지 않는다.

## 완료 기준

- 프로젝트에 정의된 빌드, 린트, 타입 체크, 포맷 체크 명령의 실행 결과가 기록된다.
- 필수 환경변수와 클라이언트 공개 설정 점검 결과가 기록된다.
- 로컬 브라우저 검증과 Apps in Toss WebView 검증 결과가 구분된다.
- 샌드박스에서 가능한 검증과 실제 토스앱 또는 QR 검증이 필요한 항목이 구분된다.
- 로그인, 오늘 문제 진입, 오디오, 선택지, 제출, 결과, 완료 화면의 실행 가능 여부가 확인된다.
- 광고와 프로모션의 mock 검증과 실제 런타임 검증 상태가 구분된다.
- MVP 출시 차단 이슈와 후속 개선 이슈가 분류되어 있다.
- 검증 중 발견된 대규모 수정이 이 작업 안에 섞이지 않는다.

## Git 전략

- 최신 `dev` 기준에서 `codex/19-build-and-toss-verification` 형식의 작업 브랜치를 만든다.
- 의미 있는 기능 단위마다 커밋한다.
- 작업 완료 후 같은 번호의 completed 문서를 작성한다.
- 작업 브랜치에서 `dev`로 PR을 보낸다.
- 예외가 필요한 작업은 이 섹션에 예외 사유와 진행 방식을 명시한다.
- 검증 중 발견한 작은 수정은 별도 커밋으로 분리하고, 범위가 큰 수정은 후속 작업으로 분리한다.
