# 20. MVP 완료 기준 체크리스트

## 목적

`daily-listen-up` MVP가 제품, 정책, UI, 기술 검증 기준을 충족했는지 최종적으로 판단할 수 있는 체크리스트를 만든다.

이 작업은 새 기능을 구현하는 작업이 아니라, 1번부터 18번까지의 결과를 바탕으로 MVP 출시 가능 여부를 판정하는 기준을 정리하는 작업이다.

## 구현 범위

- MVP 핵심 사용자 플로우 완료 여부를 체크한다.
- 하루 1문제, KST 00:00 날짜 기준, 완료 사용자 차단 정책을 체크한다.
- 답안 제출 후 전면형 광고 완료 전 결과 미노출 정책을 체크한다.
- 정답 시 토스 포인트 지급 요청 흐름을 체크한다.
- 오답 시 보상형 광고 완료 후 재도전 흐름을 체크한다.
- 중복 학습, 중복 제출, 중복 보상 방지 기준을 체크한다.
- 오늘 문제 없음, 오류, 미지원 상태 처리 기준을 체크한다.
- TDS 스타일, 모바일 WebView, safe area, 상태 문구 기준을 체크한다.
- 빌드, 린트, 타입 체크, 포맷 체크, 테스트 시나리오 통과 여부를 체크한다.
- Firebase, Toss SDK, Toss Ads, 서버 API 연동 계약 충족 여부를 체크한다.
- 완료, 조건부 완료, 미완료, 출시 차단 이슈를 구분한다.

## 제외 범위

- 체크리스트에서 발견된 문제의 직접 수정
- MVP 이후 로드맵 작성
- 운영 관리자 기능, 통계, 분석 대시보드
- 서버 구현 완료 판정
- 앱 심사 대응 문서 작성
- 비MVP 기능의 출시 기준 정의
- completed 문서 작성

## 구현 기준

- 체크 항목은 `확인 완료`, `조건부 완료`, `미완료`, `해당 없음`으로 판정할 수 있게 작성한다.
- 각 체크 항목에는 확인 근거를 남길 수 있는 위치를 둔다.
- 출시 차단 여부를 별도로 표시할 수 있게 한다.
- 기능 체크는 로그인, 오늘 문제 조회, 오디오 재생, 선택지, 제출, 광고, 결과, 보상, 재도전, 완료 화면을 포함한다.
- 정책 체크는 하루 1문제, KST `quizDate`, 결과 전 전면형 광고, 보상형 광고 재도전, 중복 보상 방지를 포함한다.
- UI 체크는 TDS 우선, 하단 CTA, safe area, 상태 문구 구분, 모바일 WebView 표시를 포함한다.
- 기술 체크는 빌드, 린트, 타입 체크, 포맷 체크, 테스트 시나리오, 환경변수, SDK 지원 여부를 포함한다.
- 서버 관련 항목은 서버 구현 완료 여부가 아니라 프론트 연동 계약과 응답 처리 기준 충족 여부로 판단한다.
- 광고와 프로모션은 mock 검증과 실제 Apps in Toss 또는 토스앱 런타임 검증 상태를 구분한다.
- 미해결 이슈는 숨기지 않고 출시 차단 여부와 후속 작업 필요 여부를 표시한다.
- 체크리스트가 새 기능 요구사항으로 변하지 않게 한다.

## 상태 및 예외 처리

- `ready_for_review`: MVP 완료 여부를 검토할 수 있는 상태다.
- `completed`: 체크 항목이 근거와 함께 충족되었다.
- `conditional`: 제한 조건이 있지만 MVP 진행이 가능한 상태다.
- `incomplete`: 체크 항목이 충족되지 않았다.
- `blocked`: 출시 또는 MVP 완료 판정을 막는 차단 이슈가 있다.
- `not_applicable`: 현재 MVP 범위에 해당하지 않는다.
- 차단 이슈가 있으면 MVP 완료로 표시하지 않는다.
- 조건부 완료 항목은 조건과 만료 기준 또는 후속 확인 기준을 함께 적는다.
- 실기기 검증이 필요한 항목은 mock 검증만으로 완료 처리하지 않는다.
- 서버 API가 미구현인 항목은 프론트 계약 준비와 실제 연동 미완료를 구분한다.

## 완료 기준

- MVP 핵심 플로우 전체에 대한 체크 항목이 있다.
- 제품 정책, UI 기준, 기술 검증, 외부 SDK 검증 항목이 분리되어 있다.
- 각 항목은 확인 상태와 근거를 기록할 수 있다.
- 출시 차단 이슈와 후속 개선 이슈를 구분할 수 있다.
- 17번 테스트 시나리오와 18번 빌드/실행 검증 결과를 근거로 연결할 수 있다.
- 광고, 프로모션, 서버 API처럼 외부 의존성이 있는 항목의 mock 검증과 실기기 검증 상태가 구분된다.
- 새 기능 구현이나 MVP 이후 로드맵 작성이 포함되지 않는다.
- 미완료 항목을 완료처럼 표현하지 않는다.

## Git 전략

- 최신 `dev` 기준에서 `codex/20-mvp-completion-checklist` 형식의 작업 브랜치를 만든다.
- 의미 있는 기능 단위마다 커밋한다.
- 작업 완료 후 같은 번호의 completed 문서를 작성한다.
- 작업 브랜치에서 `dev`로 PR을 보낸다.
- 예외가 필요한 작업은 이 섹션에 예외 사유와 진행 방식을 명시한다.
- 체크리스트 작성 중 발견한 문제는 이 작업에서 직접 수정하지 않고 별도 후속 작업으로 분리한다.

## 다음 작업과의 연결

- 이 문서는 MVP 출시 가능 여부를 판단하는 최종 기준으로 사용한다.
- `미완료` 또는 `blocked` 항목은 별도 후속 작업으로 분리한다.
- MVP 완료 후에는 1번부터 19번까지의 completed 문서를 기준으로 실제 수행 결과와 남은 리스크를 정리한다.
