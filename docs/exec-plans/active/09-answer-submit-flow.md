# 9. 답안 제출 흐름 구현

## 목적

사용자가 선택한 답안을 서버에 제출하고, 정답 여부를 공개하지 않은 채 전면형 광고 확인 단계로 이동할 수 있게 한다.

이 작업은 제출 요청과 제출 상태 전환만 다루며, 정답/오답 결과 표시와 광고 호출은 후속 작업에서 구현한다.

## 구현 범위

- 8번 작업에서 선택된 `choiceIndex`를 제출 CTA와 연결한다.
- 선택된 답안, `quizDate`, 문제 식별 값을 서버 답안 제출 API로 전달한다.
- 제출 중 상태에서 CTA와 선택지를 잠근다.
- 제출 성공 시 결과를 보여주지 않고 전면형 광고 단계로 이동한다.
- 제출 성공 후 사용자 진행 상태를 `submitted` 또는 광고 대기 상태로 전환할 수 있게 한다.
- 제출 실패 시 사용자가 다시 제출할 수 있는 오류 상태를 제공한다.
- 중복 제출과 늦게 도착한 응답을 방지하는 기준을 정의한다.

## 제외 범위

- 서버의 정답 검증 로직 구현
- 정답 여부, 정답 선택지, 스크립트, 해설 표시
- 클라이언트에서 `correctChoiceIndex`를 사용한 정답 판정
- 토스애즈 전면형 광고 SDK 호출
- 결과 화면 구현
- 포인트 지급 요청
- 오답 후 보상형 광고 재도전 처리
- 완료 화면과 중복 보상 방지 처리
- completed 문서 작성

## 구현 기준

- 제출은 사용자가 선택지를 선택한 뒤에만 가능하다.
- 제출 CTA는 TDS `Button` 사용을 우선하고 주요 액션은 `display="full"` 기준으로 배치한다.
- 제출 중에는 CTA에 `loading`과 `disabled`를 함께 적용한다.
- 제출 중에는 선택지를 변경할 수 없게 한다.
- 제출 API는 서버 세션을 기준으로 사용자를 식별하는 방식을 우선한다.
- 클라이언트가 요청 본문에 `userKey`를 넣어야 한다면 서버가 세션과 일치하는지 검증한다는 전제를 명시한다.
- 서버 API 인터페이스는 `POST /api/quiz-submissions`를 기준으로 한다.
- 요청 본문은 `{ quizDate: string; selectedChoiceIndex: number }`를 기준으로 한다.
- 필요하면 문제 식별 값 또는 `submissionSource`를 추가하되, MVP 범위를 넘는 분석용 필드는 넣지 않는다.
- 성공 응답은 `{ submissionId: string; quizDate: string; status: 'submitted'; nextStep: 'interstitial_ad' }`를 기준으로 한다.
- 제출 성공 응답에는 `isCorrect`, `correctChoiceIndex`, `script`를 포함하지 않는다.
- 제출 성공 직후 화면에는 정답 여부를 보여주지 않는다.
- 제출 성공 후 9번 전면형 광고 화면 또는 광고 대기 상태로 이동한다.
- 진행 상태는 `submitted`로 갱신하거나 서버 응답 기준으로 재조회한다.
- 같은 `submissionId`에 대한 후속 흐름을 9번과 10번이 이어받을 수 있어야 한다.
- 네트워크 오류, 4xx, 5xx 응답은 사용자에게 짧게 안내하고 재시도 CTA를 제공한다.
- 이미 오늘 완료한 사용자이거나 제출할 수 없는 진행 상태면 제출 요청을 보내지 않는다.

## 상태 및 예외 처리

- `idle`: 선택 전 또는 제출 준비 전 상태다.
- `ready`: 선택지가 있고 제출할 수 있다.
- `submitting`: 답안 제출 요청 중이다.
- `submitted`: 제출이 성공했고 전면형 광고 단계로 이동할 수 있다.
- `submit_error`: 네트워크 오류, 서버 오류, 응답 형식 오류가 발생했다.
- `already_submitted`: 같은 문제에 대해 이미 제출된 상태다.
- `completed_blocked`: 오늘 학습이 이미 완료되어 제출할 수 없다.
- 선택지가 없는 상태에서는 제출 요청을 만들지 않는다.
- 제출 CTA 연속 선택으로 같은 답안이 중복 제출되지 않게 한다.
- 제출 요청 중 페이지를 벗어나면 이후 응답이 이전 화면 상태를 덮어쓰지 않게 한다.
- 늦게 도착한 이전 요청 응답이 최신 선택이나 최신 제출 상태를 덮어쓰지 않게 한다.
- 서버가 `401`을 반환하면 로그인 상태 재확인이 필요한 상태로 처리한다.
- 서버가 `409` 또는 이미 제출된 상태를 반환하면 중복 제출로 보고 후속 상태를 재조회한다.
- 서버가 이미 완료 상태를 반환하면 문제 풀이를 중단하고 완료 흐름으로 이동한다.
- 제출 실패 후 재시도할 때 사용자가 같은 선택지를 유지할 수 있게 한다.

## 완료 기준

- 선택지가 없으면 제출 CTA가 활성화되지 않는다.
- 선택된 `choiceIndex`가 서버 제출 API로 전달된다.
- 제출 중 CTA 중복 선택으로 API가 중복 호출되지 않는다.
- 제출 성공 후에도 정답, 오답, 정답 선택지, 스크립트가 화면에 표시되지 않는다.
- 제출 성공 응답의 `submissionId`가 9번 전면형 광고 흐름으로 전달될 수 있다.
- 제출 실패 시 빈 화면이나 무한 로딩 없이 재시도할 수 있다.
- 이미 완료했거나 제출할 수 없는 진행 상태에서는 제출 요청을 보내지 않는다.
- 클라이언트가 Firebase의 `correctChoiceIndex`로 정답을 판정하지 않는다.
- 전면형 광고 호출, 결과 분기, 포인트 지급, 보상형 광고 재도전이 포함되지 않는다.

- 작업 완료 후 같은 번호의 completed 문서를 작성한다.
- 작업 브랜치에서 `dev`로 PR을 보낸다.
- 예외가 필요한 작업은 이 섹션에 예외 사유와 진행 방식을 명시한다.
- 서버 제출 API가 준비되지 않았다면 mock 또는 임시 어댑터로 프론트 상태 전환을 검증하고 completed 문서에 남긴다.
