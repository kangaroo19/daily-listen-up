# 공통 스타일 가이드라인

## 목적

이 문서는 `daily-listen-up` 앱의 UI를 일관되고 빠르게 구현하기 위한 공통 기준이다.

모든 화면은 Apps in Toss 모바일 WebView 환경에서 짧은 영어 듣기 학습을 부담 없이 완료할 수 있도록 설계해야 한다. 사용자는 화면을 오래 읽거나 탐색하지 않고도 지금 무엇을 해야 하는지 바로 이해할 수 있어야 한다.

## 기본 원칙

- TDS를 우선 사용한다.
- 한 화면에는 하나의 주요 목적만 둔다.
- 학습, 퀴즈, 보상 상태를 즉시 구분할 수 있게 표현한다.
- 사용자가 다음 행동을 고민하지 않도록 주요 액션을 명확하게 제공한다.

## TDS 사용 원칙

Apps in Toss에서 제공하는 TDS(Toss Design System)를 기본 컴포넌트와 디자인 기준으로 사용한다.

- 공식 기준은 Apps in Toss 디자인 컴포넌트 문서를 따른다: https://developers-apps-in-toss.toss.im/design/components.html
- 버튼, 카드, 배지, 리스트, 입력 요소, 상태 표시 등은 TDS 컴포넌트를 먼저 검토한다.
- 커스텀 UI는 TDS로 해결할 수 없을 때만 허용한다.
- 커스텀 UI를 만들 때도 TDS의 간격, 타이포그래피, 색상, 인터랙션 감각과 어긋나지 않아야 한다.
- 임의의 디자인 시스템이나 외부 UI 스타일을 섞지 않는다.

## 레이아웃 원칙

모든 화면은 모바일 WebView 기준으로 설계한다.

- 화면 상단에는 현재 상태나 핵심 맥락을 둔다.
- 화면 중앙에는 사용자가 처리해야 할 주요 콘텐츠를 둔다.
- 화면 하단에는 다음 행동으로 이어지는 주요 액션을 둔다.
- 관련된 정보는 가까이 배치한다.
- 서로 다른 역할의 요소는 시각적으로 명확히 구분한다.
- 같은 역할의 요소는 같은 형태와 위치 규칙을 유지한다.

화면은 위에서 아래로 자연스럽게 읽혀야 한다. 사용자가 순서를 추론해야 하는 배치는 피한다.

## 콘텐츠 원칙

문장은 짧고 직접적으로 쓴다.

- 한 문장에는 하나의 메시지만 담는다.
- 학습 상태는 사용자가 지금 무엇을 해야 하는지 중심으로 쓴다.
- 퀴즈 문항은 질문과 선택지를 빠르게 구분할 수 있게 쓴다.
- 정답, 오답, 완료, 재도전, 보상 상태는 서로 다른 의미가 즉시 드러나게 쓴다.
- 보상 관련 문구는 기대 보상과 실제 지급 상태를 혼동하지 않게 쓴다.

긴 설명보다 짧은 상태 문구와 명확한 버튼 라벨을 우선한다.

## 금지 패턴

- TDS 대신 임의의 디자인 시스템을 기본값처럼 사용하는 것
- TDS와 어긋나는 버튼, 카드, 상태 표시를 만드는 것
- 한 화면에 여러 주요 목적을 동시에 넣는 것
- 긴 설명문을 화면 안에 그대로 나열하는 것
- 핵심 액션이 화면 밖으로 밀려나는 것
- 보상, 정답, 오답, 완료 상태를 비슷한 표현으로 혼동하게 만드는 것
