# 4. 토스 로그인 기능 구현

## 목적

사용자가 Apps in Toss WebView에서 별도 ID/password 입력 없이 토스 로그인 상태를 확인하고, 로그인 완료 후 오늘의 학습 흐름으로 진입할 수 있게 한다.

## 구현 범위

- 앱 진입 또는 홈페이지 시작 CTA 선택 시 서버 세션 확인 흐름을 연결한다.
- 미로그인 상태에서 토스 로그인 필요 상태와 주요 CTA를 제공한다.
- CTA 선택 시 Apps in Toss SDK의 `appLogin()`을 호출한다.
- `appLogin()`이 반환한 `authorizationCode`와 `referrer`를 서버 로그인 API로 전달한다.
- 서버 로그인 성공 응답을 받으면 클라이언트 인증 상태를 갱신한다.
- 로그인 진행 중, 성공, 실패, 취소, 재시도 상태를 최소 UI로 처리한다.
- 이미 유효한 로그인 상태라면 토스 로그인 화면을 건너뛰고 다음 진입 흐름으로 이동한다.

## 제외 범위

- ID/password 로그인 폼 구현
- 자체 회원가입, 프로필, 로그아웃 고도화, 계정 탈퇴 기능
- 서버의 인가 코드 토큰 교환, access token 발급, refresh token 관리, 사용자 정보 조회 구현
- 클라이언트에서 Toss access token 또는 refresh token 저장
- 클라이언트에서 Toss 사용자 정보 직접 조회
- Firebase 사용자 진행 상태 조회 또는 저장
- 오늘의 문제 조회
- 영어 문제 풀이 페이지 구현
- 결과 페이지 구현
- 광고 호출과 보상 지급 요청
- completed 문서 작성

## 구현 기준

- 토스 로그인은 일반 로그인 폼이 아니라 Apps in Toss SDK 기반 인증 흐름으로 처리한다.
- `appLogin()` 호출은 화면 곳곳에 흩어두지 말고 인증 기능 영역의 얇은 래퍼 또는 서비스 함수로 모은다.
- `authorizationCode`는 일회성 값으로 보고 클라이언트에 장기 저장하지 않는다.
- `authorizationCode`와 `referrer`는 받은 즉시 서버 로그인 API로 전달한다.
- 토큰 교환과 사용자 정보 조회는 서버가 담당한다.
- 서버 로그인 API 인터페이스는 `POST /api/auth/toss-login`을 기준으로 한다.
- 요청 본문은 `{ authorizationCode: string; referrer: 'DEFAULT' | 'SANDBOX' }`를 기준으로 한다.
- 성공 응답은 `{ userKey: string }` 또는 서버 세션 설정 후 `{ userKey: string }`을 기준으로 한다.
- 로그인 상태 확인 API는 `GET /api/auth/session`을 기준으로 한다.
- 로그인 상태 확인 성공 응답은 `{ userKey: string }`, 미로그인 응답은 `401`로 처리한다.
- `userKey`는 다음 작업에서 사용자 진행 상태 기준을 정의하기 위한 최소 식별 값으로만 다룬다.
- 로그인 화면의 목적은 로그인 후 학습 시작 하나로 제한한다.
- 화면 상단에는 로그인 필요 상태를 짧게 알리고, 중앙에는 한 문장 설명을 두며, 하단에는 TDS `Button` 기반 주요 CTA를 둔다.
- 문구는 짧고 직접적으로 작성한다.
- 모바일 WebView 하단 safe area를 고려해 CTA가 화면 밖으로 밀리지 않게 한다.
- 로컬 브라우저처럼 Apps in Toss SDK를 사용할 수 없는 환경에서는 앱이 빈 화면으로 멈추지 않게 안내 상태를 제공한다.

## 상태 및 예외 처리

- `checking`: 앱 진입 직후 서버 세션을 확인한다.
- `unauthenticated`: 로그인 필요 화면을 보여준다.
- `loggingIn`: `appLogin()`과 서버 로그인 API 요청이 진행 중인 상태다.
- `authenticated`: 서버 로그인 성공 후 `userKey` 또는 인증 세션이 확보된 상태다.
- `error`: 서버 오류, 네트워크 오류, 응답 형식 오류를 짧게 안내하고 재시도 CTA를 제공한다.
- CTA 연속 선택 시 `appLogin()`과 서버 로그인 API가 중복 호출되지 않게 한다.
- 사용자가 토스 로그인 절차를 취소하거나 거절한 경우 치명적 오류로 보지 않고 로그인 필요 상태로 돌아간다.
- 서버가 `401`을 반환하면 미로그인 상태로 처리한다.
- 서버가 5xx를 반환하거나 네트워크 요청이 실패하면 오류 상태로 처리한다.
- 실패 상태에서 자동 반복 호출은 하지 않는다. 재시도는 사용자의 명시적인 액션으로만 수행한다.
- 무한 로딩, 빈 화면, 원인을 알 수 없는 오류 문구는 허용하지 않는다.

## 완료 기준

- 앱 진입 시 로그인 상태 확인 후 `authenticated` 또는 `unauthenticated`로 분기된다.
- 미로그인 사용자는 토스 로그인 CTA를 볼 수 있다.
- CTA를 연속 선택해도 `appLogin()`과 서버 로그인 API가 중복 호출되지 않는다.
- `appLogin()` 성공 시 `authorizationCode`와 `referrer`가 서버 로그인 API로 전달된다.
- 서버 로그인 성공 응답을 받으면 클라이언트가 인증 상태로 전환된다.
- 로그인 완료 후 다음 작업에서 오늘의 문제 진입 흐름을 연결할 수 있다.
- 로그인 취소, 인증 실패, 인가 코드 만료, 네트워크 실패, 서버 오류가 빈 화면이나 무한 로딩 없이 처리된다.
- 클라이언트가 Toss access token 또는 refresh token을 저장하거나 교환하지 않는다.
- `npm run build`가 통과한다.
- 프로젝트에 lint 또는 typecheck 스크립트가 있으면 해당 검증도 통과한다.

## Git 전략

- 최신 `dev` 기준에서 `codex/04-toss-login` 형식의 작업 브랜치를 만든다.
- 의미 있는 기능 단위마다 커밋한다.
- 작업 완료 후 같은 번호의 completed 문서를 작성한다.
- 작업 브랜치에서 `dev`로 PR을 보낸다.
- PR 설명에는 참조한 active 문서, 작성한 completed 문서, 서버 로그인 API 계약, Apps in Toss `appLogin()` 공식 문서 확인 여부를 함께 적는다.
- 서버 API가 아직 준비되지 않았다면 mock 또는 임시 어댑터로 프론트 동작을 검증하고, 예외 사유를 completed 문서에 남긴다.
