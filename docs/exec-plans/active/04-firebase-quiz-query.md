# 4. Firebase 문제 데이터 조회 구현

## 목적

KST 기준 오늘 날짜에 해당하는 영어 듣기 문제 1개를 Firebase에서 조회해 이후 진입 화면과 문제 풀이 화면이 사용할 수 있게 한다.

이 작업은 문제 데이터를 안정적으로 가져오는 기준을 만드는 작업이며, 오디오 재생 UI나 객관식 풀이 UI를 구현하지 않는다.

## 구현 범위

- 3번 작업에서 정의한 KST `quizDate`를 사용해 오늘 문제를 조회한다.
- Firebase `quizzes` 컬렉션의 오늘 문제 문서 조회 기준을 정의한다.
- 문제 데이터의 필수 필드와 프론트 내부 타입을 정의한다.
- Firebase 원본 데이터를 앱에서 사용할 수 있는 문제 데이터로 변환하는 기준을 만든다.
- 오늘 문제 있음, 오늘 문제 없음, 잘못된 문제 데이터, 조회 실패 상태를 구분한다.
- 문제 데이터 조회 로직을 화면 컴포넌트와 분리한다.
- 오늘 문제 없음 상태가 5번 진입 화면에서 표시될 수 있도록 결과 모델을 정의한다.

## 제외 범위

- Firebase 프로젝트 생성, 보안 규칙 전체 설계, 운영 배포 설정
- 문제 생성, 문제 수정, 관리자 업로드 화면
- AI 기반 문제 자동 생성
- 여러 문제 목록, 난이도, 카테고리, 랜덤 문제, 복습 문제
- 오디오 재생 UI와 오디오 로딩 제어
- 객관식 선택지 UI와 답안 선택 상태
- 답안 제출, 정답 검증, 결과 분기
- 전면형 광고, 보상형 광고, 포인트 지급 요청
- 사용자 진행 상태 조회 또는 저장 구현
- completed 문서 작성

## 구현 기준

- 오늘 문제 조회는 로그인 완료와 `quizDate` 확정 이후에만 실행한다.
- Firestore 조회는 페이지 컴포넌트에서 직접 수행하지 않고 `quizRepository` 또는 같은 역할의 얇은 데이터 함수로 분리한다.
- MVP에서는 하루 1문제 정책에 맞게 `quizzes/{quizDate}` 문서 ID 방식의 조회를 우선 검토한다.
- 쿼리 방식이 필요하면 `quizDate` 동등 조건으로 1개 문서만 조회하고, 다중 문제 탐색 UI는 만들지 않는다.
- 문제 데이터 필드는 다음 값을 기준으로 한다.
  - `quizDate`
  - `audioUrl`
  - `questionText`
  - `choices`
  - `correctChoiceIndex`
  - `script`
  - `promotionAmount`
- `audioUrl`은 HTTPS 원격 URL을 기준으로 한다.
- `choices`는 객관식 UI에서 바로 사용할 수 있는 문자열 배열이어야 한다.
- `choices`는 최소 2개 이상이어야 한다.
- `correctChoiceIndex`는 `choices` 배열 범위 안의 숫자여야 한다.
- `promotionAmount`는 정답 시 기대할 수 있는 프로모션 금액 표시의 입력값으로만 사용한다.
- `correctChoiceIndex`와 `script`는 데이터 계약에 포함하되, 이번 작업과 5번 진입 화면에서 사용자에게 노출하지 않는다.
- 정답 판정의 최종 기준은 서버 검증으로 보고, 클라이언트 데이터만으로 보상 지급 여부를 확정하지 않는다.
- Firebase 원본 데이터는 런타임 검증 후 앱 내부 타입으로 변환한다.
- 필수 필드가 누락되거나 형식이 맞지 않으면 `invalid` 상태로 처리한다.
- Firebase 캐시를 사용하더라도 현재 KST `quizDate`와 다른 날짜의 문제를 오늘 문제처럼 보여주지 않는다.
- 문제 조회 결과는 5번 진입 화면과 6번, 7번 후속 작업이 같은 계약으로 사용할 수 있어야 한다.

## 상태 및 예외 처리

- `idle`: `userKey`, Firebase 초기화, `quizDate`가 아직 준비되지 않았다.
- `loading`: 오늘 문제를 Firebase에서 조회 중이다.
- `ready`: 오늘 날짜 문제 데이터가 있고 필수 필드 검증을 통과했다.
- `empty`: 오늘 날짜 문제 문서가 없다.
- `invalid`: 문제 문서는 있지만 필수 필드 누락, 선택지 부족, 정답 인덱스 범위 오류가 있다.
- `error`: Firebase 초기화 실패, 권한 오류, 네트워크 오류, 알 수 없는 조회 실패가 발생했다.
- `empty`는 오류로 보지 않고 `오늘의 문제 준비 중` 상태로 전달한다.
- `invalid`는 사용자에게 상세 데이터 오류를 그대로 노출하지 않고 문제를 시작할 수 없는 상태로 전달한다.
- 조회 중 KST 날짜가 바뀌면 이전 날짜 응답이 늦게 도착해도 새 날짜 상태를 덮어쓰지 않게 한다.
- 조회 실패 시 자동 재시도를 반복하지 않는다.
- 재시도는 사용자의 명시적인 액션 또는 화면 재진입으로만 수행한다.
- 조회가 완료되기 전에는 문제 풀이 화면으로 이동할 수 없게 한다.

## 완료 기준

- KST `quizDate` 기준으로 오늘 문제 1개를 조회하는 인터페이스가 정의되어 있다.
- Firebase 원본 문제 데이터와 앱 내부 문제 타입의 필수 필드가 정리되어 있다.
- 오늘 문제 있음, 오늘 문제 없음, 잘못된 데이터, 조회 실패가 서로 다른 상태로 구분된다.
- 문제 데이터 검증 기준이 있어 잘못된 문서가 문제 풀이 화면으로 전달되지 않는다.
- `correctChoiceIndex`와 `script`를 이번 작업의 UI에서 노출하지 않는 기준이 명확하다.
- 문제 조회 로직이 화면 컴포넌트에서 직접 Firebase SDK를 다루지 않도록 분리 기준이 있다.
- 여러 문제 탐색, 랜덤 문제, 복습 문제처럼 하루 1문제 정책을 벗어나는 기능이 포함되지 않는다.
- 5번 진입 화면이 문제 조회 결과를 사용해 시작 가능, 준비 중, 오류 상태를 분기할 수 있다.
- 6번과 7번 작업이 같은 문제 데이터 계약을 이어받을 수 있다.

## Git 전략

- 최신 `dev` 기준에서 `codex/04-firebase-quiz-query` 형식의 작업 브랜치를 만든다.
- 의미 있는 기능 단위마다 커밋한다.
- 작업 완료 후 같은 번호의 completed 문서를 작성한다.
- 작업 브랜치에서 `dev`로 PR을 보낸다.
- 예외가 필요한 작업은 이 섹션에 예외 사유와 진행 방식을 명시한다.
- Firebase 보안 규칙이나 정답 데이터 노출 정책이 확정되지 않았다면 completed 문서에 남기고, 클라이언트 정답 검증으로 보상 지급을 확정하지 않는다.

## 다음 작업과의 연결

- 5번 작업은 이번 작업의 `ready`, `empty`, `invalid`, `error` 상태를 사용해 오늘의 문제 진입 화면을 분기한다.
- 6번 작업은 `audioUrl`을 받아 오디오 재생 UI를 구현한다.
- 7번 작업은 `questionText`와 `choices`를 받아 객관식 퀴즈 UI를 구현한다.
- 8번 작업은 사용자가 선택한 답안과 문제 식별 값을 서버 검증 요청으로 연결한다.
- 10번 작업은 서버 검증 결과를 기준으로 결과 화면에 필요한 정답 정보 노출 범위를 결정한다.
