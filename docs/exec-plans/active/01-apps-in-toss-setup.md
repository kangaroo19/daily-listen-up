# 1. Apps in Toss 기본 앱 구조 세팅

## 목적

Apps in Toss 모바일 WebView 안에서 React 앱이 안정적으로 실행되는 기본 구조를 만든다.

이 작업의 목표는 학습 기능을 제공하는 것이 아니라, 이후 토스 로그인, 사용자 식별, 문제 조회, 광고, 보상 기능을 같은 구조 위에 순서대로 붙일 수 있는 기반을 마련하는 것이다.

## 구현 범위

- React + TypeScript 기반 앱의 기본 프로젝트 구조를 만든다.
- Apps in Toss WebView 기준의 앱 엔트리와 공통 앱 셸을 구성한다.
- 모바일 WebView 기준의 viewport, safe area, 기본 레이아웃 기준을 잡는다.
- TDS 사용을 전제로 공통 UI 구조와 전역 스타일 기준을 마련한다.
- ESLint, Prettier, TypeScript 설정을 준비한다.
- `dev`, `build`, `preview`, `lint`, `typecheck`, `format`, `format:check` 실행 스크립트를 준비한다.
- Firebase 클라이언트 SDK 초기화 위치를 만든다.
- Toss SDK 접근 위치를 만든다.
- Toss Ads 연동 위치를 만든다.
- 서버 API 호출용 공통 클라이언트 위치와 요청/응답 처리 기준을 만든다.
- 환경변수 로딩과 필수값 검증 기준을 만든다.
- 앱 부팅 상태를 표현할 최소 상태를 준비한다.

## 제외 범위

- 실제 Toss 로그인 호출과 로그인 결과 처리
- 인가 코드 교환, 사용자 조회, 사용자 식별 처리
- Firebase 문제 데이터 조회
- Firebase 사용자 진행 상태 조회와 저장
- 오디오 재생 UI
- 객관식 퀴즈 UI
- 답안 제출 처리
- 전면형 광고 호출과 완료 처리
- 보상형 광고 호출과 재도전 처리
- 정답 검증 요청
- 토스 포인트 지급 요청
- 정답, 오답, 완료, 문제 없음 화면 구현
- 서버 구현과 서버 비밀값 관리
- 후속 화면을 미리 만드는 목업 작업

## 구현 기준

- 프로젝트는 React + TypeScript 단일 앱 구조로 시작한다.
- 빌드 도구는 Apps in Toss 권장 구조를 우선하고, 별도 기준이 없으면 Vite 기반으로 구성한다.
- TypeScript 설정은 Apps in Toss 또는 프로젝트 초기 템플릿 기본값을 우선한다.
- 경로 별칭은 템플릿 기본값 또는 기존 프로젝트 기준을 따른다.
- ESLint, Prettier 설정은 Apps in Toss 또는 프로젝트 초기 템플릿 기본값을 우선한다.
- 템플릿 기본값만으로 결정되지 않는 설정값이 있으면 임의로 정하지 않는다.
- 폴더 구조는 최소 책임 단위로 시작하고, 필요 이상으로 세분화하지 않는다.
- `src/app`은 앱 엔트리, provider 조합, 앱 셸, 부팅 상태 분기를 담당한다.
- `src/pages`는 화면 단위 컨테이너를 담당한다.
- `src/features`는 로그인, 퀴즈, 광고, 보상 기능이 들어갈 위치만 정의한다.
- `src/lib/firebase`는 Firebase App과 Firestore 인스턴스 초기화 위치를 담당한다.
- `src/lib/toss`는 Toss SDK 접근과 런타임 확인 위치를 담당한다.
- `src/lib/toss-ads`는 Toss Ads 접근 위치와 공통 인터페이스를 담당한다.
- `src/services/api`는 서버 API 공통 요청, 응답 파싱, 에러 매핑 기준을 담당한다.
- `src/shared/config`는 환경변수 읽기와 필수값 검증을 담당한다.
- `src/shared/ui`는 공통 레이아웃, 로딩 화면, 오류 화면처럼 여러 화면에서 재사용할 UI를 담당한다.
- Firebase, Toss SDK, Toss Ads, 서버 API는 화면 컴포넌트에서 직접 초기화하지 않는다.
- 환경변수는 `import.meta.env`에서 읽고, 앱 내부에서는 검증이 끝난 설정 객체를 사용한다.
- 클라이언트 환경변수에는 공개 가능한 값만 둔다.
- 토큰 교환용 비밀값이나 서버 비밀키는 클라이언트에 두지 않는다.
- 기본 화면은 `앱이 정상적으로 준비되었는지 보여주는 것` 하나만 목적으로 둔다.
- 아직 제공하지 않는 기능을 사용할 수 있는 것처럼 보이게 하지 않는다.
- TDS를 우선 사용하고, 커스텀 UI는 필요한 경우에만 만든다.

## 상태 및 예외 처리

- 앱 부팅 상태는 최소 `bootstrapping`, `ready`, `initFailed`로 구분한다.
- 초기화 중에는 로딩 또는 준비 중 상태를 보여준다.
- 초기화 완료 시에는 단일 기본 화면을 보여준다.
- 필수 환경변수가 누락되면 앱이 조용히 실패하지 않게 한다.
- Firebase 초기화 실패와 Toss SDK 런타임 확인 실패는 원인을 구분할 수 있게 한다.
- 로컬 브라우저에서 Toss 런타임이 없는 경우 앱 전체가 죽지 않게 한다.
- Apps in Toss 외 환경에서는 지원 환경이 아니라는 점을 짧게 안내한다.
- 초기화 실패 화면에는 재시도 또는 새로고침 기준을 제공한다.
- 무한 로딩, 빈 화면, 의미 없는 오류 문구는 허용하지 않는다.
- SDK 초기화와 설정 로딩은 중복 실행되어도 부작용이 없어야 한다.

## 완료 기준

- React + TypeScript 앱이 로컬에서 실행된다.
- Apps in Toss WebView에서 기본 앱 화면이 정상 표시된다.
- 모바일 WebView 기준의 기본 레이아웃이 준비되어 있다.
- `npm run build`가 통과한다.
- `npm run lint`가 통과한다.
- `npm run typecheck`가 통과한다.
- `npm run format:check`가 통과한다.
- Firebase 클라이언트 SDK, Toss SDK, Toss Ads, 서버 API 접근 경계가 분리되어 있다.
- 환경변수 검증 기준이 있고, 필수값 누락을 확인할 수 있다.
- 공통 로딩 화면과 공통 초기화 실패 화면이 준비되어 있다.
- 실제 로그인, 문제 조회, 광고 호출, 보상 요청 로직은 들어가 있지 않다.
- 2번 이후 작업이 앱 진입 구조를 다시 설계하지 않고 이어질 수 있다.

## Git 전략

- 이 작업은 초기 환경 설정 작업이므로 별도 작업 브랜치를 만들지 않는다.
- 최초 1회 `main` 기준으로 `dev` 브랜치를 만든 뒤, `dev` 브랜치에서 예외적으로 진행한다.
- 의미 있는 기능 단위마다 커밋한다.
- 작업 완료 후 `completed/01-apps-in-toss-setup-result.md`에 실제 수행 내용을 기록한다.
- 1번 작업은 이후 작업 브랜치의 기준이 되는 `dev` 초기 기반을 만드는 작업으로 본다.
